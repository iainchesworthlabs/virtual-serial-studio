# 08 Engine gap analysis and the backend adapter

The designs ask for some things the engine does not expose, or exposes in another shape. Every row of this table was read against the source (last pass: November 2026), and names the function, type or file that carries it. Never change `vss_core` semantics to suit the GUI without an explicit task. Prefer a thin addition in `vss_studio`, and say so in the PR.

## The adapter rule
One narrow interface sits between the GUI and the engine: `vss::gui::StudioBackend` (`apps/vss_gui/src/backend/studio_backend.hpp`), with `EngineStudioBackend` over a `vss::studio` and `FakeStudioBackend` for tests. `StudioBackend::caps()` returns a `capabilities` struct of booleans (`backend/capabilities.hpp`). Screens call the adapter, never the engine directly. Each feature checks its capability and, when absent, degrades visibly (disabled with a tooltip "Not available in this build", or a simpler variant) instead of failing or faking it.

## Capability table
| Capability the UI needs | Status | Plan if missing |
|---|---|---|
| Create, list, remove virtual ports (auto, pty, loopback, windows-driver) | Provided (`studio::create_virtual_port`; `virtual_port_kind` also has `named_pipe`, Windows only) | Use directly. The window offers no named pipe; it only makes one again when a deleted one is brought back by Undo. |
| Enumerate serial devices and com0com pairs | Known (`vss_cli devices`) | Use directly. |
| Links: connect, split, join, redirect, monitor, merge policy interleave or owner | Known | Use directly. |
| Owner arbitration: set owner, release owner | Provided by the hub (`hub::set_owner`, `hub::release_owner`). `vss::studio` has no method of its own for it and hands out the hub (`studio::engine()`) | `StudioBackend::set_owner` and `release_owner` call the hub, and the Owner bar uses them (`capabilities::owner`). |
| **Shared bus link** (several ports on one wire, each hears all the others) | Provided by `vss_core` (`link_mode::bus`, `hub::bus`) and `vss::studio::bus`; `"mode": "bus"` with `members` in the JSON | The engine backend sets `capabilities::shared_bus`. A backend without it keeps the star (a split from the master with a join tap): the Connect dialog shows "Shared bus" disabled with the tooltip "Not available in this build", the JSON editor says "Bus links are not available in this build" for a file that has one, and nothing simulates a bus out of other links. A bus has no modem lines and no owner, so the Line wiring and Owner tools skip it. |
| **Half-duplex bus behaviour** (report two stations sending at once, a turn-around time, gate on RTS) | Provided by `vss_core` (`link_options::half_duplex`: a line rate, a turn-around time, collisions reported or garbled, `event_kind::bus_fault`, `link_stats::collisions` and `garbled`) and the topology JSON (`half_duplex` on a bus link). RTS gating applies only to a member whose transport reports the other side's RTS in step with the bytes (`transport::reports_peer_rts`), which today is the loopback port: the Windows driver port reports the program's RTS only when asked, so it is not gated. No echo of a station's own bytes | The engine backend sets `capabilities::half_duplex_bus`. A backend without it shows **Half-duplex line** in Connect ports and in the bus's settings disabled with the tooltip "Not available in this build", and the JSON editor says "Half-duplex buses are not available in this build" for a file that has `half_duplex`. The RTS control says which ports it applies to. A port still has no electrical-mode label. To gate a driver port the driver must hand the hub the RTS in line with the bytes; until then the port is not gated, never gated wrongly. |
| **A device on another computer as a bus member** | Provided: an `rfc2217-listen://` endpoint can be a bus member, and `allow=` limits who connects | With nobody connected the member is silent, which looks like an unplugged device and is the right behaviour. The ports list and the inspector say "No remote connected" or "Clients connected: N" (`endpoint_info::clients`, from `listen_transport`). Time is stamped once, in Studio, never by the other computer. |
| **Ports another program made** (a `vss_cli` process, another Studio) shown with live state and watched | **Not provided.** A Windows driver port belongs to the process that made it: its hub end takes one handle and the port is removed when that process ends. The hub is in-process, with no registry or server another process can read. `enumerate_serial_devices` lists the COM names (the driver's devices have a `VSSCOM\` hardware id) but no owner, state or traffic. Opening the COM name takes the application end from a program that has it, and is not a read-only copy | `capabilities::external_ports` is off in every backend. `StudioBackend::other_program_ports()` names the driver ports Studio does not hold. The Ports dock shows a note under the list, the Watch window explains an empty or incomplete list with a "Create a port" action, and nothing pretends to show the port. The engine change that would remove the gap is in the PR that added this row: a per-machine port registry or service that every process can query, with owner, state and a read-only tap on the traffic (the driver would need a second hub-side observer interface for that). Needs the owner's decision; it is not a `vss_studio` addition. |
| **Ports that outlive the window** (a background agent that owns the engine) | **Not provided.** The engine runs inside the process that made the studio, so the ports live as long as `vss_gui` (or `vss_cli run`) does | The GUI keeps itself running instead: closing the window hides Studio in the notification area, one Studio runs per user, the running setup is kept and starts again after a restart, and Studio can start at sign-in. See `10-running-in-the-background.md`. A Studio crash still stops the ports, and `vss_cli` keeps its own hub. The engine change that removes both is a per-user `vss_agent` that owns the studio, with Studio and `vss_cli` as clients over a local pipe or socket (a `RemoteStudioBackend`); the same agent closes the row above. Needs the owner's decision and its own PRs: `docs/agent.md` is the design and the list of decisions, with a first slice (`vss_agent` and `vss_cli agent`, loopback ports only) that Studio does not use yet. |
| Cycle refusal on add link | Known (engine refuses) | Map the error to the loop pattern. "Show the loop" computes the cycle from the link graph in the GUI. |
| Events, counters, bounded traffic ring buffer | Known | Subscribe through the sink, marshal to the GUI thread, batch by refresh interval. |
| Set DTR, RTS, BREAK. Read CTS, DSR, DCD, RI | Known | Use directly. Unsupported lines return an error, show a disabled control. |
| Null-modem crossing with an on or off switch (`emulate_modem_lines`) | Known | Use for "Emulate modem lines". |
| **Per-link line wiring matrix** | Provided by `vss_core` (`modem_wiring` in `link_options`, `hub::set_link_wiring`) | The engine backend sets `capabilities::line_matrix` and the matrix is editable. A backend without it shows the Standard preset read-only. The wiring is not saved in the topology JSON. |
| **Link delay and jitter** | Provided by `vss_core` (`delay_ms` and `jitter_ms` in `link_options`) and the topology JSON (`delay_ms`, `jitter_ms` on any link, a bus included) | Settings... on a link of the Advanced canvas (the link's menu, or Alt+Enter) opens `LinkSettingsDialog` with Delay and Jitter; the link is changed in place (see the row on changing a link). Connect ports and the Inspector have no control for it. It can also be set in the JSON editor or a topology file, and the Advanced JSON check places a bad value on its line. A link with a delay keeps it through save and open. |
| **Fixture sends, echo and a byte generator** | `endpoint::write` on a mock hands bytes to the device, which only records them. Sending *from* a fixture needs the mock's receive path. The scripted device (`vss::responder`) matches bytes that arrive on a port and replies fixed bytes, so it cannot echo a fixture, count or randomise. | `vss::studio::inject_data` (thin forwarding, like `inject_fault`) makes a fixture speak: `EngineStudioBackend::send` uses it for a mock. `vss::studio::set_fixture_echo` sends back every byte written to a fixture. `capabilities::fixture_echo` says the backend has it; without it Echo is disabled with "Not available in this build". The byte generator (text line, fixed pattern, counter, random bytes) is plain sends on a GUI timer, bound to the fixture, and needs no capability. A scripted device from a JSON script file is not exposed in the window yet. |
| Fault injection on fixtures and Windows driver ports | Provided by `vss_studio` (`studio::inject_fault` with `fault_kind`). A fixture takes all six: parity, framing, overrun, break, hang-up, disconnect. A Windows driver port takes parity, framing, overrun and break, raised at the program that has it open through `vss::raise_driver_line_error`; hang-up and disconnect are refused there | `StudioBackend::inject_fault`, gated by `capabilities::faults` for a fixture and `capabilities::driver_faults` (true when the Studio driver is installed) for a driver port. The Advanced Lines panel has an "Inject a fault" section with one button for each kind; they are disabled, with the reason, unless the port is a running fixture, or a running driver port with a program on it (the peer-open state) for the four line errors. |
| **Program speed, listener clients and a speed mismatch** | Provided by `vss_core` (`endpoint_info::peer_format` and `clients`, filled by the transport) and `vss::studio::format_mismatches` | The engine backend sets `capabilities::line_format`. The ports list and the inspector say "Program set 19200 7E2" where the platform can tell (a Windows driver port reads it from the driver, a Linux or macOS pseudo terminal from `tcgetattr`), "No remote connected" or "Clients connected: N" for a listener, and in the warning colour "Differs from X in baud rate or framing" when the ports of a link run at different speeds. A port that cannot tell says nothing: never a guessed speed, and a port with an unknown speed never causes the warning. The texts follow the data: a backend that does not fill `peer_format` and `clients` shows none of them. The flag itself is read only by the port's Settings dialog. |
| **Peer-open detection** ("Waiting for program", "Program connected") | Provided for a pseudo terminal on Linux and for a port of the Studio driver on Windows (`vss::peer_open`, `studio::peer_states`; the driver tells Studio when a program opens or closes the port). Unknown on macOS and for every other kind of port (loopback, named pipe, device, network, fixture) | The adapter carries a tri-state `peer_state` (`unknown`, `not_open`, `open`) in `port_view::peer`, read once a second while `capabilities::peer_open` is on. "Open" is the normal state. Show "Waiting for program" and "Program connected" only where the adapter reports a definite `not_open` or `open`, and say nothing about an outside program on `unknown`. Never claim what you cannot know. |
| **COM number of a driver port** (choose it when the port is made, change it afterwards) | Provided by `vss_ports` (`create_driver_port(..., com_number)`, `set_driver_com_number`) and `studio::create_virtual_port` / `studio::set_com_number` | `capabilities::com_numbers` is true when the Studio driver is installed. Add port shows a COM number field and the Inspector a Change... button only then; without it neither is shown, or the button is disabled with "Not available in this build". `StudioBackend::set_com_number` restarts the port (a second or two), so a dialog calls it from a worker thread and calls `refresh()` afterwards. A refusal is explained beside the number (`com_number_refusal`), never as a bare engine message. |
| **Which COM numbers Windows keeps** (to offer only free numbers) | Provided by `vss_ports` (`reserved_com_numbers`: the COM name database, `ComDB`, readable by every user, and the names that resolve) and `studio::reserved_com_numbers`. The list of present ports is not enough: the database keeps the number of a port that is unplugged or was removed, and the driver refuses such a number with `already_exists` after it has made and removed the port (Windows plays its connect and disconnect sounds) | `StudioBackend::reserved_com_numbers()` returns the numbers, or `nullopt` where the computer cannot be asked (not Windows, or the database cannot be read). Simple mode offers COM numbers only while it has the list: without it the row shows "New port" and says Studio picks a free one, and Studio's own choice (`EngineStudioBackend::create_port_with_com_number`) still steps past a refusal. A number refused anyway is named in the failure and not offered again. Never guess which numbers are free. |
| **Release a port held by a program** | Provided by `vss_ports` (`revoke_driver_port`, `describe_process`, `terminate_process`) and `studio::revoke_port` / `studio::driver_holder` | `capabilities::release_port` is true when the Studio driver is installed. Advanced mode shows Release port... in the Inspector for a driver port that reads Program connected. The dialog names the holder and says how long no data has passed (never that the program is stuck), then takes the port back (the driver's revoke request) or ends the process. `terminate_process` ends only the user's own processes unless Studio is elevated and never tries otherwise; the dialog shows that choice off with the reason. |
| **Reopen a port, retry a lost connection, recreate lost driver ports** | Provided by `vss_core` (`endpoint::reopen`) and `vss::studio` (`reopen`, `set_reconnect_policy`, `lost_ports`, `recreate_lost_ports`) | The engine backend sets `capabilities::recreate_ports`. While any Windows driver port is lost the shell shows a banner with **Recreate ports**, run on a worker thread because making a port takes seconds; a failure leaves the banner and says why in the status bar. A backend without the flag shows no banner and does not claim the ports are fine. Retrying a dropped `tcp://` or `rfc2217://` client is an engine and `vss_cli run --reconnect` feature; the window has no control for it yet. |
| Setup check inputs (com0com present, elevation, dialout membership) | Provided: `detect_com0com` (no administrator rights needed) through `studio::detect_com0com`, and the rest by platform helpers in the GUI layer | `support/setup_facts.cpp` (`probe_platform_facts`): elevation from the process token on Windows and the user id elsewhere, membership of the serial group on Linux only. `vss::permissions::probe` adds the protection facts of the row below. |
| "Install com0com" and "Restart as administrator" | GUI actions, both built | Never install silently. Install com0com is offered only when neither the Studio driver nor com0com is found; it opens an instructions dialog with a button to open the project page (the URL is in one function, `com0com_project_url`). Restart as administrator starts Studio again elevated with `--replace`, on Windows only, and is offered only when Studio is not elevated and the Studio driver is not in use. |
| **Elevation and operating-system protections** (UAC, Windows Firewall; Linux serial access, confinement and firewall; macOS firewall, Local Network and sandbox) | **Provided by `vss_ports`** (`vss/ports/permissions.hpp`) | A `fact` for each topic with a reason code and an honest `unknown` where the platform cannot be asked, and two elevated steps, each taken only after the user agrees: the Windows Firewall rule for a listener, made by `vss_cli permissions firewall-allow`, and adding the user to the serial group on Linux (`add_user_to_group`, through `pkexec`). `capabilities::firewall_rule` gates the server role in Connect ports; the permission and firewall dialogs ask `firewall_step_available()` and `group_step_available()` (`support/elevated_step.cpp`), and without the step explain and show the command, with "Not available in this build". `capabilities::serial_group_step` is set but nothing reads it. Studio never elevates, changes a rule or a setting, or turns a protection off without that button. |
| Free com0com pair count for the share wizard | Provided in the GUI layer; no engine API | `free_com0com_pair_paths` (`dialogs/share_plan.cpp`) takes the pairs from `StudioBackend::devices()` and drops every pair that has an end a port already holds. With the Studio driver installed the wizard does not use com0com pairs: it plans driver ports against the per-user limit (`make_driver_share_plan`). |
| Create one more com0com pair from the share wizard | Provided in the GUI adapter. `vss::create_com0com_pair` exists in `vss_ports`; `vss::studio` has no facade for it, and the call needs elevation | `StudioBackend::create_com0com_pair()` (no library change) asks for elevation and picks numbers above the highest COM in use. `capabilities::com0com_pair_creation` is false on Linux and macOS, and the wizard's button follows it. |
| Share as one operation with rollback | Known (share scenario, failed bridge rolls back) | Use directly. |
| **Add or remove a program port on an existing share** | Provided by the engine: `hub::add_target` and `hub::remove_target` add or take off one target of a duplex link (a connect or a split) in place | `backend/share_edit` creates the port and adds it as a target (`add_program_port`), and takes a port off the link before removing it (`remove_program_port`). The link keeps its id, options, owner and counters, and the other programs lose no bytes. A failed step puts the setup back as it was: a new port that cannot be added is removed again, and a port that cannot be removed is added to the link again. The last program of a share is removed with its port, and the link goes with it. One-way links and buses have no `add_target`; the engine returns `unsupported`. |
| Remove a whole setup | Known (`remove_port` on each port; links go with them) | The GUI finds the ports joined by links (`shell/setup_group`) and removes them one by one, naming them in the confirmation. |
| Bridge by URI (`tcp://`, `udp://`, `rfc2217://`), client role | Known | Build the URI in the GUI, preview it, pass it through. |
| **Network bridge in the server role** (listen for other computers) | **Provided by `vss_ports`** (was missing in Boost.VirtualSerial) | Boost.VirtualSerial's `tcp_bridge_port` and `udp_bridge_port` only resolve and connect. `vss_ports` adds `listen_transport`, which `vss::studio::attach_serial` opens for `tcp-listen://host:port` and `udp-listen://host:port`; the GUI's server role builds those URIs. `capabilities::network_server` is true for the engine backend. A backend without it keeps the old behaviour: the dialog defaults to the client role and the server option is disabled with "Not available in this build". `rfc2217-listen://host:port` is the RFC 2217 access server (Telnet with the COM-PORT option); see `design-deviations.md`. Never simulate a listener. |
| JSON topology load, save, validate | Known (`vss_config`) | Use directly. |
| JSON validation errors with line and column | A line, never a column. `vss_config` returns an error code with no position | The GUI finds the line itself (`advanced/json_validation.cpp`): a syntax error from the offset `QJsonDocument::fromJson` reports, a schema error from an index of where each field starts. A problem with no position has line 0, and the editor then hides "Go to line". `capabilities::json_positions` is set but nothing reads it. |
| Rename port | Provided by `vss_studio` (`studio::rename_port`) | The studio renames the endpoint, its records and a pseudo terminal's stable link together. `capabilities::rename_port` is true for the engine backend. A backend without it hides the menu item and F2. |
| Undo and redo | Not in the engine; a snapshot restore is not exact | The GUI keeps a history of changes with an exact inverse (connect and remove a link, change an owner, rename). Changes made on the Advanced canvas are recorded by port name, not id, so they survive ports being made again: adding a bundle is undone by removing its ports, and deleting ports is undone by making them again with the same name, kind, settings, COM number and links (`backend/canvas_edit`); the status bar names a port that came back on a different path. Any other change to the set of ports still clears the history. No snapshot is restored and there is no Undo toast; confirmations stay. |
| **Change a port's serial settings after it is made** | Not in `vss_core` (`endpoint_options` is fixed when the endpoint is made) | Provided by a thin `vss_studio` addition, `studio::reconfigure_port`: a fixture gets a new fixture under the same endpoint, a device or `rfc2217://` client is opened again through `endpoint::reopen`, and a virtual port or loopback only saves the values (the program sets its own speed). `studio::port_settings` returns the current values, because `endpoint_info::serial` keeps the first ones. `capabilities::port_settings`; without it the Settings dialog is read-only with "Not available in this build". `tcp://` and `udp://` have no line settings. |
| **Change a link's delay, jitter, policy, modem lines or half-duplex line** | `hub::set_link_options` changes them on a link that exists | The canvas calls `StudioBackend::set_link_options` (`change_link_options` in `backend/canvas_edit`); the link keeps its id, ports and counters. A delay change discards the bytes the old delay still holds; leaving the owner policy clears the owner; a change to a bus's half-duplex line discards what is on the wire and starts the collision and garbled counts again. Undo changes the options back in place. |
| Benchmark | Provided by `vss_studio` (`vss::run_benchmark`, with progress and cancel), used by `vss_cli bench` and the window | `StudioBackend::run_benchmark`, gated by `capabilities::benchmark`. `BenchmarkDialog` runs it on a worker thread. |
| Diagnostic bundle zip | Not in the engine; built in the GUI layer with no new dependency | `StoredZipWriter` (`support/zip_writer.cpp`, stored entries only), the contents and their redaction in `support/bundle.cpp` and `support/redact.cpp`, and the dialog under File (`capabilities::diagnostics`). |
| Event log tab | Not in the engine; built in the GUI layer | `support::EventLog` is fed from the batched hub events and is what the diagnostic bundle writes; `EventLogPanel` is the Log tab of Advanced mode. |
| Recent files, templates | Not in the engine; built in the GUI layer | Recent files are a `QSettings` list (`ui/recentFiles`, `dialogs/recent_files.cpp`). The templates are four JSON files bundled as Qt resources (`dialogs/templates/`), read through `vss_config` when they are loaded. |
| Node positions in topology | Not in JSON | Session only. Do not change the JSON schema. |
| Simple-mode setup name and options | Not in JSON | The program label is the port's name, which the file keeps. A setup's own name and the "Let me type" and "Show me the data" choices are session only until the schema owner agrees a field for them. |
| Simple-mode setup kind | Not in JSON | Read back from the ports and links (`simple/setup_kinds`), so a file or an Advanced-mode drawing shows the same way. Anything no job describes is listed as made in Advanced mode. |
| Simple-mode Change | In-place edit of the targets of a duplex link (`hub::add_target`, `hub::remove_target`), the sources of a one-way link (`hub::add_source`, `hub::remove_source`) and the members of a bus (`hub::add_member`, `hub::remove_member`) | Change edits the link in place for attach, share and take turns when the device stays the same, for send into one (a join) when the receiver stays the same and the policy is interleave, and for a bus: it adds the new ends first, takes off the ones that close and removes their ports, so the link id, its options and its owner stay and the other ports lose no bytes. A failed step puts the link back as it was (an end that was taken off and put back goes to the end of the list). Pair, port with echo and network setups, a different device or receiver, a change of kind, and a bus whose new members would take it past 64 before the old ones leave still disconnect the old link and make the new one. Programs on kept ports keep them open; only bytes in flight during the swap can be lost. |
| Take turns with replies | Provided by the engine: the owner policy arbitrates only the routes that meet at one endpoint | On a duplex link (connect, split) those are the routes from the targets back to the source, so the owner is one of the targets; what the source sends reaches every target whoever owns the link. Simple mode's "take turns" is a split from the device to the programs with the owner policy, and `set_owner` names the program that sends. Only the owner's bytes reach the device, and the device's replies reach every program. On a join (the Advanced "Switch" tile) the owner is one of the sources, as before. |

## Flags without a row

`capabilities` has more flags than the table has rows. These say that a whole area exists and are true in the engine
backend; a backend without one loses the menu items and dialogs of that area: `create_ports`, `devices`, `links`,
`fixtures`, `share`, `bridge`, `setup_check`, `undo`.

Three flags are set and read by nothing in the window: `control_lines` (the line controls follow
`port_view::supports_control_lines`, which is per port), `json_positions` and `serial_group_step` (both in their rows
above). They are listed here so that nobody takes them for a gate that works.
