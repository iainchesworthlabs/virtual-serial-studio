Plugins and integrations

A plugin connects Studio to something else: a test framework that drives it, a computer that watches it, or a simulated device that answers through it. The official plugins are the Pro edition.

In development

Studio can run plugins: Tools, Plugins lists the plugins on this computer, and Plugin isolation and trust says how one is checked and run. The official plugins on this page are being built and none can be downloaded yet. The page describes what the first version will contain. Details may change. The control endpoint and the Python client below are not plugins and are in the Community edition.

The control endpoint and the Python client

The control endpoint lets a program on the same computer drive Studio. It is the program vss_gate, and a Python client for it is in the repository. Both are in the Community edition and need no licence, and so are the JUnit reports of a run. A test script uses them to make and link ports, send bytes, wait for bytes and read the event and traffic streams.

Community, free

Where to get them
Both are in the repository on GitHub and neither is in the installers or the packages yet. The endpoint, vss_gate, and the agent behind it, vss_agent, are built from source. The Python client is in adapters/python: use it from that folder, or install it with pip install ./adapters/python.
Who can reach the endpoint
Only programs on the same computer. By default that is a local socket for your own account. You can also turn on TCP on the loopback address, where every connection needs a token that you make.
Reports of a run
A script can open a named run, record what passed and what failed, and ask the endpoint for the result as JUnit XML, for a CI system to collect. This is in the Community edition too.
From the command line
vss_cli control does the same from a shell: status, port create, port rename, port remove, link, unlink, send, expect, watch, run begin and run report, and token create, token list and token revoke. vss_cli is in the installers and packages, but the commands need vss_gate running.
What the Python client needs
Python 3.9 or later and no other package.
What they cannot do yet
A port made through the endpoint is a loopback port inside the agent, so another program cannot open it. Faults and response timing cannot be set through it.
From another computer
Controlling or watching Studio from another computer is a Pro plugin. Remote control and remote monitoring.

Response timing and fault injection

A test harness can set and change these during a run.

Response timing

A delay or jitter on a reply, fixed or drawn from a distribution. Slow a simulated device to the speed of the real instrument, or past your program's timeout.

Scripted replies

When this pattern arrives, answer with that, after this long, a given number of times or in a set order.

Fault injection

Drop, corrupt, truncate or duplicate a reply. Raise a line error, or drop a control line at the moment you choose.

Repeatable runs

A deterministic mode with a seeded random source, so a repeated run makes the same decisions. Real times still depend on the machine.

One clock

A timestamp on everything the harness sees, from a single clock, so events on different ports can be put in order.

Timing in the engine

The engine carries out the delays, replies and faults that a test sets as rules, and the RS-485 turnaround delay, without waiting for a plugin. An action is never early, and the engine records how late each one was.

Remote control and remote monitoring

A Pro plugin lets one other computer control or watch a running Studio, such as a CI machine or a rig controller. It uses the same control endpoint, which is off until you turn it on. Both computers of a seat hold the same licence file. There are three levels of access, and each needs more setup than the one before.

  1. Local only, the default. A local socket that only programs on the same computer and account can reach.
  2. Token. You make a token on the receiving side and give it to the sending side. A token can be revoked and can be limited to certain actions.
  3. Administrator control. OAuth 2.0 and OpenID Connect with an external identity provider, and the client credentials grant for unattended rigs, for sites that manage access centrally.

Plugin isolation and trust

A plugin is a folder that you or your administrator add, and Studio never downloads one. It runs as a program of its own, apart from Studio, and only after you have decided about that version. If it crashes it cannot take Studio down, and its code never runs inside the window.

Your decision
Review and decide lists the plugin's name, version and fingerprint, what it adds and every permission it asks for. A permission that the plugin marks as optional can be unticked. A signature shows who made a plugin and that its files are unchanged. It does not show that the plugin is safe.
A changed plugin asks again
Your decision is kept for that version of the plugin only. If its files change, Studio asks you again.
Isolation on Windows
A plugin is confined in an AppContainer. It can read its own folder and write its data folder, it reaches no other file of yours, and it has no network unless that was granted.
Isolation on Linux and macOS
Studio does not confine a plugin there yet, and the Plugins page says so. An official plugin runs without confinement. Any other plugin runs only if you choose Run without isolation for that version, where your administrator allows it, and then it has your own access to your files and the network.
A plugin that fails
Studio starts it again after 1, 2, 4 and 8 seconds, and stops trying after the fifth failure in ten minutes. Start again tries once more.
Adding and removing
Add a plugin, on the Plugins page, looks into the folder and shows what it found before anything is copied. From a shell, vss_cli plugin has list, verify, install, remove and run.
Official only, if you want
An administrator can set a policy that allows only official plugins.
Write your own
The plugin API is documented and free to use in every edition: the plugin framework and the plugin API, message by message. The official plugins that we build on it are commercial. A plugin declares what it extends, its settings and its permissions in a manifest, and its author chooses its licence. We do not support third-party plugins.
What a plugin can extend
Generators that put bytes or traffic patterns onto a port, fixture types that answer like a real instrument or modem, behaviour modifiers that delay, corrupt, filter or rewrite traffic on a link, and adapters that let other tools drive Studio.
